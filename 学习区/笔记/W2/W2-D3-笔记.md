### 1c. 等亮度不同色（选做，30 分钟；时间不够直接跳过，记入第 5 节债务）

`EdgeDetection.shader:21` 的亮度系数：`dot(color, half3(0.2125, 0.7154, 0.0721))`。

> 工程是 **Linear 色彩空间**（`ProjectSettings.asset:50` `m_ActiveColorSpace: 1`），边缘检测挂在 `AfterRenderingSkybox`，在 tonemapping 之前。所以 shader 采到的是**线性值**，手算必须用线性值；而 Inspector 颜色面板显示的是 sRGB 值。
> 换算：sRGB → 线性 `L = ((s + 0.055) / 1.055)^2.4`；线性 → sRGB `s = 1.055 · L^(1/2.4) − 0.055`（s、L 都在 0–1）。

步骤：先定颜色 A 为纯红，在**线性空间**里求亮度相等的纯绿 G，再换回 sRGB 填进 Inspector。

- 颜色 A：线性 (1, 0, 0)，亮度 = 0.2125
- 颜色 B：线性 (0, 0.2970, 0)，亮度 = 0.2125 → 换成 sRGB 填 Inspector：G = 0.5812
- 计算过程：g = 0.2125 ÷ 0.7154 = 0.2970；s = 1.055 × 0.2970^(1/2.4) − 0.055 = 0.5812。<span style="color:red">计算器里指数 `(1 ÷ 2.4)` 必须加括号，否则 `^` 只吃到 1。g 曾两次输错被除数（1.2115、0.2115），应为 0.2125 ÷ 0.7154；结果必须在 0–1 之间。</span>

用两个 Unlit 材质分别填这两个颜色，并排摆放：交界处是否描边？预期：不描边 → 实际：**不描边**（红绿交界无线，只有外轮廓对背景有线；Game 视图 1920×1080）

> 8 位颜色有量化误差，两边亮度只能「近似相等」。若出现很淡的线，Frame Debugger 只能目测，要读两侧实际像素值需用 RenderDoc（W4 再装）。

**检查点**：三个实验中，哪个和代码推理一致？哪个不一致？不一致的原因是什么？ __<span style="color:red">1a、1b、1c 都与推理完全一致</span>，三类边都漏画。1c 两侧亮度只是近似相等（输入舍入 + `B10G11R11` 精度），残差约 0.001，产生的边缘强度接近 0，肉眼不可见。<span style="color:red">（曾误判 1c「不一致」：残差是精度问题，不是推理错）</span>__

### 2a. 手算 σ = 2 的 5 点核（30 分钟）

| 偏移 i | -2 | -1 | 0 | +1 | +2 |
|---|---:|---:|---:|---:|---:|
| a(i)，σ = 2 | 0.6065 | 0.8824 | 1 | 0.8824 | 0.6065 |
| w(i)，σ = 2 | 0.1525 | 0.2218 | 0.2514 | 0.2218 | 0.1525 |
| w(i)，σ = 1（抄 D1） | 0.0545 | 0.2442 | 0.4026 | 0.2442 | 0.0545 |

## 6. 复习（今天顺带弄懂的概念）

### 漫反射公式

> 漫反射 = 表面颜色 × 光的颜色 × max(0, N·L)

### 一帧的渲染流程（CPU → GPU）

1. **CPU 录制命令**：每帧每相机一次。每个 pass 至少录一个 draw，
   C# 里设置的参数（如 `_BlurSpread`）也在这时写入，每帧只算 1 次。
2. **提交**：一帧的命令整批交给 GPU。draw 不合并，各自独立执行。
3. **GPU 按顺序执行每个 draw**：
   - **顶点着色器**：次数 = 这次 draw 的顶点数，每次处理 1 个顶点，并行执行。
   - **图元装配**（固定硬件）：按索引把算好的顶点拼回三角形 → 剔除背面。
   - **光栅化**（固定硬件）：找出三角形覆盖的像素 → 插值 uv 等数据。
   - **片元着色器**：次数 = 目标 RT 上被覆盖的像素数，并行执行。
     C# 传来的参数对所有像素都一样；shader 里写的计算每个像素都要算一遍。
   - **写入目标 RT**。
4. **输出到屏幕**：最后由 BlitFinalToBackBuffer 拷到屏幕。

| draw | 顶点着色器 | 片元着色器 |
|---|---:|---:|
| 全屏 pass，256×256 | 3（一个比屏幕大的三角形） | 65536 |
| 一个 Cube，看得见的面覆盖 3000 像素 | 24（6 面 × 4，每面法线/uv 独立） | 约 3000 |

**推论**
- 每加一个全屏 pass，就多付一次「整屏像素数 × 每像素采样数」。
- `downSample = 2` → RT 变成 1/4 大小 → 片元次数变成 1/4。
- 两个物体在屏幕上重叠 → 重叠区域被算两遍（overdraw）。
- SRP Batcher 省的是 CPU 准备命令的开销，片元次数不变。

### GPU 的三种并行

1. **数据并行**（最主要）：同一 draw 里，大量顶点/像素同时跑同一段 shader，只是输入不同。
   GPU 分组执行：NVIDIA warp 32 个一组，AMD wavefront 32/64 个一组，组内同一时刻执行同一条指令。
   例：65536 个像素 ≈ 2000 组，分给几十个计算单元同时跑。
   → W3 伏笔：同组像素走不同 if 分支时，两条分支都要跑一遍。
2. **流水线并行**：各阶段同时开工，处理不同批次。前面的三角形在跑片元，后面的还在跑顶点。
3. **draw 之间**：结果按提交顺序生效；不冲突时硬件可部分重叠。
   后一个 pass 要读前一个 pass 写的 RT（如模糊纵向读横向结果）→ 必须等写完（依赖 / barrier）。

### 为什么先拆成顶点、再装回三角形

- **拆**（顶点着色器）：每个顶点独立计算、互不依赖 → 可以大批并行。
  还能**复用**：Cube 12 个三角形按三角形算要 36 个顶点，实际只有 24 个不同顶点；
  索引缓冲（index buffer）记录「哪 3 个顶点组成一个三角形」，同一顶点只算一次、多个三角形共用。
- **装**（图元装配）：光栅化要回答「这个三角形盖住哪些像素」、插值 uv 也要 3 个顶点的值 →
  必须拿到完整三角形。装配是光栅化的需要，不是为了并行。

```
顶点（各自独立，并行算，算一次复用）
  → 图元装配（按索引拼回三角形）
  → 光栅化（三角形 → 覆盖的像素）
  → 片元（各自独立，并行算）
```

**规律**：能拆成彼此独立的小单位 → 并行算；必须看整体的步骤 → 交给固定硬件。
