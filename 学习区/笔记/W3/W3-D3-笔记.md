## 1. tile 存储模型（30 分钟）

**对照图**：讲 IMR 看[02-传统立即模式渲染](../../图片/W3/D3/02-传统立即模式渲染.png)，讲 TBR 看[04-基于图块的渲染](../../图片/W3/D3/04-基于图块的渲染.png)，tile memory 在芯片哪里看[03-tile-memory在芯片上的位置](../../图片/W3/D3/03-tile-memory在芯片上的位置.png)。三张图分别经 V31、V33、V32 查证后落地。

【原文】[Arm · Tile-Based Rendering §2，pp.7–8](https://documentation-service.arm.com/static/636dfb934e6cf12278ad8c27) 的传统立即渲染（Immediate Mode Rendering，IMR）模型按图元组织处理；缓存可保留最近访问的帧缓冲数据。不能把逻辑更新说成每画完一个三角形就直接写外部显存。

【原文】同文 §3，pp.9–10 的分块渲染（Tile-Based Rendering，TBR）先建立图元与屏幕块的关系，再处理块内片元。颜色、深度、模板工作集可放片上 RAM；不需保留的附件可以不写回外部内存。

【推断·范围】本节只用共同的 tile 存储模型，不以此定义基于分块的延迟渲染（Tile-Based Deferred Rendering，TBDR）。按一块说明流程是教学简化，不能据此断言整颗 GPU 同时只处理一块。tile memory 与通用缓存只比较片上位置，不视为同一种存储。

**自测前提**：只讨论上述 TBR 模型，不猜 GPU tile 大小、并行数量或先后顺序；附件指本次渲染使用的颜色、深度等目标。

1. tile memory 位于片上还是外部内存？与 W3-D2 的缓存位置作类比时，不能把什么等同起来？ __tile memory位片上，<span style="color:red">不能把tile memory与cache等同起来（曾错写成「因为片上交互不需要消耗带宽说以不能等同」：没说出把什么和什么等同，理由也区分不了两者）</span>__。
2. 假设颜色结果需要保留给后续使用，解释保存与丢弃的区别；不要把所有临时附件都算作必须写回：__需要保存的话本块计算完之后就会写回内存 不需要只是临时计算使用就可以告诉mali不需要写回内存直接丢弃就行__。

## 2. 附件 Load / Store 与纹理采样（35 分钟）

**对照图**：一张目标从开始 Load 到结束 Store 的先后顺序看[05-Load与Store的时间顺序](../../图片/W3/D3/05-Load与Store的时间顺序.png)，经 V34 查证后落地。

【原文】[Unity 6.3 · RenderBufferLoadAction，Description / Properties](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Rendering.RenderBufferLoadAction.html) 定义的是开始向渲染目标渲染时如何处理该目标的旧内容。Load 保留旧内容；DontCare 不要求保留，tile GPU 可免去旧内容加载；Clear 清除内容，同页原文注明目前只配合 RenderPass API 生效。（2026-10-18 按 F27 补）

**开始 / 结束两个枚举（2026-10-18 按 F31 补，V36 查证）**：

| 枚举 | 什么时候选 | 可选值 |
|---|---|---|
| `RenderBufferLoadAction` | 开始向这张目标渲染时，处理目标旧内容 | Load、Clear、DontCare |
| `RenderBufferStoreAction` | 这张目标渲染完时，处理新结果 | Store、Resolve、StoreAndResolve、DontCare |

【原文】[Unity 6.3 · RenderBufferLoadAction，Description](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Rendering.RenderBufferLoadAction.html)「When the GPU starts rendering into a render target…」；[Unity 6.3 · RenderBufferStoreAction，Description](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Rendering.RenderBufferStoreAction.html)「when the GPU is done rendering into it」。

【推断·读法】Load、Clear、DontCare 是同一个枚举里三个并列的值，一次选一个，没有父子关系。枚举名里的 Load 指「开始时」这一组，值 Load 指保留旧内容，两者不是一回事。一张目标开始、结束各选一次，两次互相独立，例如开始 DontCare、结束 Store。两个枚举都有 DontCare，名字相同、时刻不同；本节自测第2题说的是开始那组。

【原文】[Arm §3，pp.9–10](https://documentation-service.arm.com/static/636dfb934e6cf12278ad8c27) 说明 tile 内完成处理后可将结果写回外部内存；不需保留的附件可以省去保存。

【推断·区分】本节用「附件 Load」指目标旧内容进入 tile 的加载，用「Store」指需要保留的结果写出。着色器读取另一张源纹理属于纹理采样（texture sampling），不能仅因它读了以前的结果，就称为当前目标的附件 Load。实际读取还可能命中缓存。

**自测前提**：tile GPU 附件模型；第 2 题旧内容已经无用，后续只读取已经写入或清除过的像素。

1. 用「目标旧内容」和「新结果」分别解释附件 Load、Store：__<span style="color:red">Load是DDR到tile memory搬的是「目标旧内容」 store是tile memory到DDR搬运的是「新结果」（曾错写成「Load是DDR中「目标旧内容」到tile memory「新结果」store是tile memory中「目标旧内容」到DDR中「新结果」」，后又写反成「Load是tile memory到DDR……store是DDR到tile memory」）</span>__。
2. DontCare 相比 Load 可能省掉哪项工作？为什么必须限定旧内容不再需要？ __<span style="color:red">省掉从DDR读取到tile memory读取的工作（曾错写成「从tile memory读取到DDR」）</span>因为<span style="color:red">dontcare就是不读取旧内容（曾错写成「dontcare就是不读取旧内容不保存新内容」：结束时写不写回由 StoreAction 另选）</span>，<span style="color:red">Load 保证读到的是旧内容，DontCare 不保证；为了不读到这种不确定的值，必须限定旧内容已经不需要了（曾错写成「因为tile memory空间有限 旧内容如果不清理新内容没空间加载进去」）</span>__。

**算账前提**：仅为数据体积模型；颜色目标 1920×1080，单采样、无 MSAA，假设完整 Store 一次及完整附件 Load 一次。每像素字节用 W3-D2 第 9a 节核对后的实际格式换算值，先记录为 __4__ 字节；`1 MB = 1,000,000 字节`。忽略缓存、压缩、对齐和其他流量。本题不代表后处理必然产生一次附件 Load。

3. 一张目标的数据体积 = 宽 × 高 × 每像素字节。分别算一次 Store 和一次附件 Load 的理论 MB，再写合计：__8.2944 MB和8.2944 MB合计16.5888 MB__。这些数字能否直接称作实测新增显存流量？ __不能__。

**算账前提里「忽略的四项」是什么（2026-10-19 按 F37 补，V39 查证）**：

【推断·范围】上题的 8.2944 MB 是一张 1920×1080、每像素 4 B 的目标跨一次芯片边界的理论数据量：Store 是 tile memory → 外部内存，附件 Load 是外部内存 → tile memory。Fragment Shader 和 tile memory 之间的片上读写不算在内。实际外部内存流量还会因下面四项和它不一样：

1. 缓存（cache）：【原文】[Arm · The Bifrost Shader Core，p.7](https://documentation-service.arm.com/static/655f28652c8b3557fee70876) 的 L2 缓存由各 shader core 共用，作用是减少重复读取，典型每核 64–128 KB。【推断】本题一次完整 Store、一次完整 Load，每份数据只搬一次，目标又远大于 L2，缓存省不下多少。
2. 压缩（compression）：【原文】[Arm · Tile-Based Rendering，p.10](https://documentation-service.arm.com/static/636dfb934e6cf12278ad8c27)：Mali 写出 tile 颜色数据时可用无损压缩 AFBC（Arm Frame Buffer Compression），写出时省带宽，之后每次读回这张帧缓冲也省；同页的 Transaction Elimination 在 tile 颜色没变时跳过写出。所以 Store、附件 Load 两侧实际都可能更少。
3. 对齐（alignment）：【原文】数据按固定大小的块搬运，例如 [NVIDIA CUDA Best Practices §10.2.1](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#coalesced-access-to-global-memory) 的 32 字节事务；[D3D12 · Uploading texture data through buffers](https://learn.microsoft.com/en-us/windows/win32/direct3d12/upload-and-readback-of-texture-data) 说纹理资源是「unknown texture layout」。【推断】纹理在显存里的布局由驱动决定，可能有补齐，多出多少要看设备。
4. 其他流量【推断】：同一帧还有贴图、顶点数据、需要保存时的深度（不需保留的附件不写回，【原文】同 Arm p.10）和其他 pass 的读写；上题只算这一张颜色目标的一次 Load、一次 Store。
