## 1. 为什么先找瓶颈（15 分钟）

**前提**：Unity 6.3 手册；W5-D1、D2 的测法。

1. **先测再改**：【原文】[Unity 6.3 · Reduce rendering work on the CPU or GPU](https://docs.unity3d.com/6000.3/Documentation/Manual/OptimizingGraphicsPerformance.html)「Before you make any changes, you must profile your application to identify the cause of the problem.」（译：做任何改动之前，必须先分析应用，找出问题的原因。）
2. **CPU 和 GPU 修法不同**：【原文】同页「rendering-related performance problems can occur on the CPU or the GPU」（译：和渲染有关的性能问题可能出在 CPU，也可能出在 GPU。）【推断】所以第一刀是分清是哪一边慢；慢的不是 GPU，GPU 上省再多也不会让帧变快。
3. **GPU 慢在哪一侧**：【原文】同页「If an application is limited by fill rate, the GPU is trying to draw more pixels per frame than it can handle.」（译：如果应用受填充率限制，就是 GPU 每帧想画的像素比它能处理的多。）
4. **怎么判断像素那一侧**：【原文】[Unity 5.1 · Optimizing Graphics Performance](https://docs.unity3d.com/510/Documentation/Manual/OptimizingGraphicsPerformance.html)「Does running the game at lower display resolution make it faster? If so, you’re most likely limited by fillrate on the GPU.」（译：用更低的显示分辨率运行游戏会变快吗？会的话，你多半受 GPU 填充率限制。）
   - 【推断】这是旧版手册，6.3 手册没有这句；方法本身不依赖版本。
5. **编辑器里测只是近似**：【原文】[Unity 6.3 · Collect performance data introduction](https://docs.unity3d.com/6000.3/Documentation/Manual/profiling-collect-data-introduction.html)「Profiling in Play mode doesn’t give you an accurate reflection of what the performance of your application looks like on a real device.」（译：在 Play 模式下分析，不能准确反映应用在真机上的性能。）
   - 【原文】[Unity 6.3 · Collect performance data in Play mode](https://docs.unity3d.com/6000.3/Documentation/Manual/profiling-play-mode.html) 建议最大化 Play 视图：「open it in a maximized view to run your application at a resolution closer to that of your target device」（译：最大化打开它，让应用以更接近目标设备的分辨率运行。）
   - 【推断】所以今天的结论都要写「在编辑器里」。
6. **瓶颈不只 CPU、GPU 两类**：【原文】[Unity 6.3 · FrameTiming](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/FrameTiming.html) 官方示例给瓶颈分了几类，其中三类是：
   - 「PresentLimited, // Limited by presentation (vsync or framerate cap)」（译：受呈现限制（垂直同步或帧率上限））
   - 「CPU, // Limited by CPU (main and/or render thread)」（译：受 CPU 限制（主线程和 / 或渲染线程））
   - 「GPU, // Limited by GPU」（译：受 GPU 限制）

**在哪读数**
- **做**：每帧点中后，看 Highlights 下方明细的 Frame time 一栏，抄 CPU Active Time 和 GPU Time。条上读不到数字时，鼠标悬停 Highlights 图上那一帧看摘要。再切到 CPU Usage 的 Timeline，抄这一帧 DXGI.WaitOnSwapChain 的 ms，第一帧时记下它在哪条线程：**Main Thread**。

## 今天学到了什么（收口）

1. **找瓶颈之前，先验尺子**：像素多 16 倍，GPU Usage 读数却不涨（2.64 / 2.725 / 2.525 ms）。这不是说场景不卡像素，而是这把尺子没量到大部分 GPU 工作。这是你测出来、觉得不对才发现的（F83）。
2. **GPU Usage 在 URP 下看不全**：【原文·代码】GPU Usage 模块旁的提示（UnityCsReference 6000.3 `GPUProfilerModule.cs:36-37`）：「the profiler won't show most GPU markers if these renderers are enabled」（译：启用这些渲染器时，分析器不会显示大部分 GPU 标记。）本工程是 URP。
3. **编辑器里的 Highlights GPU Time 也不能用**：20–58 ms 又大又跳。【推断】编辑器其他窗口也在用 GPU，会混进同一帧（V76 第 2 条）。
4. **测量会改变读数，又一次**：开着 GPU Usage 测 CPU，CPU 读数会被拉高（F81，你发现的黄色警告）。W5-D1 的 Gizmos、窗口数也是这个道理。
5. **要量准，就离开编辑器**：【原文】[Unity 6.3 · Collect performance data introduction](https://docs.unity3d.com/6000.3/Documentation/Manual/profiling-collect-data-introduction.html)「Profiling in Play mode doesn’t give you an accurate reflection of what the performance of your application looks like on a real device.」（译：在 Play 模式下分析，不能准确反映应用在真机上的性能。）
   - 所以第 3、4 节改在开发版构建里重测（V78）。
6. **Highlights 是总额，GPU Usage 是明细**：Highlights 每帧给 CPU、GPU 两个总数，用来判断谁慢；GPU Usage 把 GPU 时间拆到每个 pass。目标帧时间只是预算线，红标表示超了它，不是尖峰（Atlas 答疑）。
7. **编辑器 vs 构建，差几十倍**：试测时编辑器里 Highlights 的 GPU 是 20–58 ms，开发版构建里是 0.440 ms（第 3 节试测行）。编辑器量的是整个编辑器的活，构建只有游戏。
8. **构建的分辨率不看 Game 视图**：本工程是全屏窗口、默认按屏幕原生分辨率；用启动参数 `-screen-width`、`-screen-height` 换分辨率，一个包就能测三档（第 3、4 节）。发布游戏也要构建，只是不勾 Development Build。
9. **这一帧谁都不慢，是在等上屏**：开发版构建 1920×1080 下，10 帧中间值 CPU Active Time 0.7065 ms、GPU Time 0.2725 ms，DXGI.WaitOnSwapChain 1.114 ms 比两者都长（第 3 节）。不是 CPU 受限，也不是 GPU 受限（题 1）。
   - 【推断】按 FrameTiming 示例的判法算是受呈现限制（PresentLimited）。判法要两个条件：主线程等 Present 超过 0.5 ms；GPU、主线程、渲染线程都小于 0.8 × 整帧。
   - 你没有直接读 FrameTiming 字段，是拿图 02 那一帧的数套进去的：等待 1.16 > 0.5；GPU 0.27、主线程干活约 0.645，都小于 0.8 × 1.81 ≈ 1.45。
   - 【推断】原因不是示例注释说的垂直同步或帧率上限：本工程两档都是 `vSyncCount: 0`，脚本里也没设 `targetFrameRate`。这里等的是交换链排队（maxQueuedFrames 默认 2）（V87）。
10. **DXGI 等待不在 CPU Active Time 里**：【观察】10 帧里 DXGI.WaitOnSwapChain 都比 CPU Active Time 长，这是你 10-28 自己核对出来的。【推断】它被当作等待，从 CPU Active Time 里扣掉了（第 3 节，V80）。
11. **落不落后一帧看谁慢**：【观察】你录的一整帧 Timeline 里，渲染线程一直在等主线程送命令，主线程一 Submit，它就处理同一帧 N。【推断】只有渲染线程被 GPU 拖住（Gfx.WaitForPresentOnGfxThread 有时间）时，主线程才先进下一帧。这一帧错开一帧的是主线程（做 N）和上屏（等 N−1）（图 02，V86）。
12. **DXGI 等待只记主线程干等的那段**：【推断】它约等于「N−1 上屏的时刻 − 主线程干完第 N 帧的时刻」；N−1 已经先上屏时约为 0（图 02，V84、V86）。
13. **GPU 时间 = 固定部分 + 跟着像素走的部分**：960×540 → 1920×1080 像素 4 倍、GPU Time 2.36 倍；1920×1080 → 2560×1440 像素 1.78 倍、GPU Time 1.70 倍（题 2）。
   - 【推断】不随分辨率变的活（比如阴影贴图，本工程 `PC_RPAsset.asset:46` `m_MainLightShadowmapResolution: 2048`）在低分辨率时占比大，把倍数拉低；分辨率越高，GPU Time 越接近跟着像素数涨。
14. **瓶颈 ≠ 浪费**：瓶颈是最慢、决定整体快慢的那一环；这份活该不该做，是另一回事（题 2，Atlas 答疑）。
15. **两把尺子量出的数不能相除**：W5-D2 的 0.049 ms 是编辑器 GPU Usage 里 CopyColor、CopyDepth 两个 pass 相加，今天的 0.274 ms 是构建里的整帧 GPU Time，拿来算百分比没有意义（题 3）。
16. **卡在上屏时，降分辨率几乎换不来帧率**：【推断】960×540 比 1920×1080 的 GPU Time 少 0.158 ms，但主线程还是在等上屏，整帧时间几乎不变；先挑哪项改动，要看第 9 条的瓶颈在哪（题 3）。
