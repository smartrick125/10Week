## 1. 为什么先把场景压成 GPU 受限（15 分钟，读）

1. **D3 的结论**：原设置（1920×1080、`iterations = 1`、`downSample = 2`）下，主线程大半时间在等上屏，不是 CPU 慢也不是 GPU 慢（D3 今天学到了什么第 9 条）。
2. **压不成，改了也看不出**：【推断】GPU 不是最慢的那一环时，GPU 省下的时间只会变成更长的等待，整帧不变（D3 第 16 条）。
3. **Render Scale 是什么**：【原文】[Unity 6.3 · URP Asset reference](https://docs.unity3d.com/6000.3/Documentation/Manual/urp/universalrp-asset.html) Quality 一节 Render Scale「This slider scales the render target resolution (not the resolution of your current device).」（译：这个滑块缩放的是渲染目标的分辨率（不是你当前设备的分辨率）。）
   - 你 10-30 在包里用 Frame Debugger 看到：屏幕 2560×1440，`_CameraTargetAttachment` 是 5120×2880，像素是原来的 4 倍。
4. **10-30 试测的三档**（单帧，`iterations = 4`、`downSample = 1`）：
   - 2560×1440、Render Scale 1：CPU Active Time 1.162 ms、GPU Time 1.033 ms、DXGI.WaitOnSwapChain 1.681 ms。还是在等上屏。
   - 3840×2160：包里的 `_CameraTargetAttachment` 仍是 2560×1440，全屏被屏幕分辨率限制，没测。
   - 2560×1440、Render Scale 2：CPU Active Time 1.206 ms、GPU Time 4.589 ms、DXGI.WaitOnSwapChain 3.280 ms，表头 CPU 4.49 ms。
5. **怎么判这一帧是 GPU 受限**（Render Scale 2 那一帧，都是单帧值）：整帧取表头 CPU 4.49 ms，0.8 × 4.49 ≈ 3.59；GPU Time 4.589 > 3.59，CPU Active Time 1.206 < 3.59，所以算 GPU 受限。
   - 【原文】[FrameTiming](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/FrameTiming.html) 示例判 GPU 受限：GPU 时间大于 0.8 × 整帧，主线程、渲染线程都小于 0.8 × 整帧。
   - 【原文】[cpuFrameTime](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/FrameTiming-cpuFrameTime.html)「time between ends of two frames, which includes all waiting time」（译：两帧结束点之间的时间，包含所有等待）。所以整帧用含等待的那个数。
   - 【推断】用 CPU Active Time 代替示例里主线程、渲染线程两个数。GPU Time 比整帧还大，是因为 GPU 的帧边界和 CPU 错开（D3 第 3 节：不拿来相减）。
   - 【推断】DXGI 等待变长，是主线程在等 N−1 上屏（maxQueuedFrames = 2），上屏要先等 GPU 画完。
   - **DXGI 等待不拿来和 CPU、GPU 比谁大**：它不是干活，只说明主线程在等；等谁，要看 GPU Time 接不接近整帧。
   - 【观察】你第 3 节已抄的第 1、2 帧：CPU Active Time + DXGI 是 1.185 + 3.261 = 4.446，表头 4.45；1.259 + 3.188 = 4.447，表头 4.43。
   - 【推断】说明表头 CPU ≈ CPU 干活 + 主线程等待，不含 GPU 时间。条件：CPU Active Time 取的正好是主线程那条，主线程上的等待几乎只有 DXGI。
   - 【推断】CPU 和 GPU 同时干活，一帧多长由慢的一方决定，不是两者相加。DXGI 字面上是等上屏，上屏要先等 GPU 画完（maxQueuedFrames = 2）；GPU 慢时，等上屏实际就是在等 GPU。D3 那一帧 DXGI 也长，GPU 却只有 0.27 ms，等的是上屏本身。
   - **为什么乘 0.8**：【原文】[FrameTiming](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/FrameTiming.html) 示例代码的常量 `kNearFullFrameTimeThresholdPercent = 0.2f`，GPU 时间大于 0.8 × 整帧就算「接近整帧」；示例没写为什么取 0.2。
   - 【推断】GPU 和 CPU 的帧边界错开，两个数对不齐（第 1 帧 GPU 5.01 比表头 4.45 还大），所以不要求相等，到 80% 就算接近。

## 今天学到了什么（收口）

1. **只有改到瓶颈上，整帧才跟着变快**：Render Scale 2 下两个包都是 GPU 受限（第 7 节两张中间值表，GPU Time 都大于 0.8 × 表头 CPU，CPU Active Time 都小于它）。
   - 两步比一步 GPU Time 中间值短 3.449 ms，表头 CPU 短 4.005 ms，两者接近（题 4）。
   - GPU Time 差值远大于浮动（19.9 倍）；表头 CPU 差值也大于浮动，但只有 1.72 倍。
   - D3 原设置下 GPU 不是瓶颈，【推断】判断去掉一个 pass 整帧不变短（题 2，没实测）。
2. **选改动之前先估量**：去掉 downsample 只省 0.0655 ms，比 GPU Time 浮动 0.669 ms 小，10 帧也分不出是改动还是波动（第 5 节、题 1）。
   - 所以新改动先各测 1 帧：差值超过浮动就各测 10 帧，超过 2 倍算稳；比浮动小就换改法（第 6 节题 1 追加，F90）。
3. **整帧可以用 CPU Active + DXGI 估**（你自己的发现，题 2）：D3 中间值 0.7065 + 1.114 ≈ 1.82，和整帧 1.81 接近。
   - 0.7065、1.114 是 D3 第 3 节 10 帧的中间值，1.81 是图 02 那一帧的单帧值，不是同一组帧。
   - 【推断】条件同第 1 节第 5 条：CPU Active Time 取的正好是主线程那条，主线程上的等待几乎只有 DXGI。
   - 两个数相加只是近似：第 7 节两步版第 3 帧（Frame 2943）1.569 + 3.501 = 5.07，比表头 4.89 多 0.18。
4. **判瓶颈时 DXGI 不和 0.8 × 整帧比**：GPU Time、CPU Active Time 各自和 0.8 × 整帧比（【原文】[FrameTiming](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/FrameTiming.html) 示例，见第 1 节第 5 条）。
   - 【原文】同一示例判 PresentLimited 时，拿 present 等待和 `kNonZeroPresentWaitTimeMs = 0.5f` 比，用来判是不是在等上屏。
   - 【推断】DXGI.WaitOnSwapChain 就是示例里的 present 等待；等谁，要看 GPU Time 接不接近整帧（题 2）。
5. **downSample 让模糊范围变大**：【推断】偏移按读的那张图的纹素尺寸走（`GaussianBlur.shader:29-31` 用 `_BlitTexture_TexelSize`）。
   - RT 缩小后一个纹素盖住更多屏幕像素，同样的偏移在屏幕上走得更远；代价是缩小时丢掉细节（题 3）。
6. **采样次数数的是 shader 里调了几次采样函数**（Atlas 11-03 答疑）：双线性过滤（bilinear filtering）由硬件做完。
   - 【原文】[Bilinear Texture Filtering (Direct3D 9)](https://learn.microsoft.com/en-us/windows/win32/direct3d9/bilinear-texture-filtering)「calculate the weighted average of the 4 texels closest to the sampling point」（译：计算离采样点最近的 4 个纹素的加权平均）。
   - 【原文】同页「this routine is implemented in modern graphics hardware」（译：这个过程在现代图形硬件里实现）。
   - 【推断】这页是 D3D9 文档，本工程 D3D12 也这样由硬件做。
   - 【推断】HLSL [Sample](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/dx-graphics-hlsl-to-sample) 一次调用返回一个过滤后的颜色，所以一次调用算一次采样，不算成 4 次。
   - 【推断】本 shader 用的 `sampler_LinearClamp`（`GaussianBlur.shader:36` 等），名字里的 Linear 就是双线性。
